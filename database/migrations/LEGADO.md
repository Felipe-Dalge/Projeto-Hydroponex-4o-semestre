# Migração de base relacional legada, preservando dados

O DDL fornecido não contém INSERTs nem configuração de uma base em uso. A persistência detectada na aplicação é JSON, atendida pelo importador executável `001_importar_json.php`. Não aplicar ALTERs automáticos ao modelo Oracle sem conhecer os dados: várias relações são ambíguas. Este é o roteiro de migração paralela caso exista uma base relacional externa ao projeto, a converter em SQL executável **após** preencher e validar os mapas abaixo.

1. Inventariar servidor/versão, tabelas, colunas, constraints e contagens reais. Registrar o snapshot e parar escritas para a extração final. Exportar backup integral, inclusive senhas já hasheadas, armazenando-o fora da pasta pública com acesso restrito. Testar restauração.
2. Criar destino separado e vazio; instalar `hydroponex.sql` sem seed. Conservar base antiga intacta e somente leitura no corte. Para Oracle, usar exportação de dados por ferramenta apropriada; o DDL mistura `NUMBER`/`VARCHAR2`, `DATETIME` e `RESTRICT` e não constitui uma implantação Oracle validada.
3. Carregar exportações em **staging separado**, como textos/JSON sem truncar valores. Preservar tabela, PK original e registro integral. Não desativar constraints do destino. Criar mapas revisáveis `map_usuario`, `map_estado`, `map_cidade`, `map_cep`, `map_horta`, `map_planta`, `map_cultura`, `map_estrutura`, `map_reservatorio`, `map_sensor`, `map_monitoramento`, `map_nutriente`, cada um com chave original textual e nova chave numérica. Os nomes são especificação de staging; não são tabelas incluídas no schema final.
4. Emitir relatório bloqueante: PK nula/duplicada, órfãos, emails duplicados, campos obrigatórios ausentes, valores além de INT/DECIMAL, pH inválido, estados com sigla duplicada e nomes ambíguos. Não truncar IDs `NUMBER(100)` nem converter Estado textual diretamente para inteiro. Não usar `INSERT IGNORE` ou `REPLACE` para contornar erros.
5. Estado → cidade: inverter `Estado.fk_Cidade_ID_Cidade`. Para cada cidade há de existir um estado inequívoco. Cidade → CEP: inverter `Cidade.fk_CEP_ID_CEP`; um CEP pode ter várias cidades candidatas no modelo incorreto. Exigir resolução documentada. Normalizar CEP numérico para oito dígitos só se original estiver entre 0 e 99999999, integral e a regra nacional for confirmada. Zeros não podem ser reconstruídos para dados arbitrários fora desse domínio. Usuário → CEP: inverter `CEP.FK_Usuario_Id_usuario`; se um usuário tiver vários CEPs, escolher endereço principal com responsável, preservando os demais registros no staging. Não apagar alternativas.
6. Importar usuários com emails reconciliados. Só transportar hashes se reconhecidos e validados para `password_verify`; senha em texto puro ou hash desconhecido exige redefinição, usuário inativo e `senha_hash=NULL`. Nunca copiar segredo bruto para o destino final ou logs. Preservar `tipo` como descrição, sem conceder autoridade.
7. Importar hortas e associações `Usuario_celula → usuario_horta`. Duplicatas exatas podem virar um vínculo, mantendo relatório da consolidação. O legado não tem papéis: criar mapa de papéis aprovado e selecionar proprietário por horta; não elevar todos os membros automaticamente. Horta sem proprietário permanece arquivada até resolução.
8. Inverter `Horta.fk_Estrutura_id_estrutura`: múltiplas hortas para mesma estrutura exigem decisão de domínio antes de atribuir horta. Não duplicar estruturas físicas silenciosamente. Consolidar os dois campos de reservatório da estrutura somente se iguais ou um nulo. Se divergirem, bloquear. Reservatórios órfãos ou usados em mais de uma horta exigem atribuição/revisão; o destino exige uma horta por reservatório.
9. Culturas: preservar todos os IDs e atributos como catálogo; mover cada `Cultura.fk_Celula_id_horta` para `horta_cultura`. Não deduplicar culturas por nome sem decisão explícita. Inverter `Horta.id_planta` para atribuição de `planta.id_horta`: se uma planta tiver várias hortas candidatas ou nenhuma, resolver manualmente. Planta sem cultura identificável mantém cultura nula; não inferir por nome. Preservar `nivel_irrigacao` com unidade ainda não confirmada. Status fora do domínio exige mapa aprovado e preservação do texto original em staging.
10. Nutrientes: preservar classificação/descrição/tipo e definir nome explícito quando ausente no legado. Sensores: preservar nutriente opcional, resolver horta/instalação e unidade em mapa; não há informação suficiente para inferir horta apenas de nutriente. Não inventar aplicações de nutrientes para preencher `reservatorio_nutriente`.
11. Monitoramentos: transportar descrição e data com fuso de origem identificado. Definir horta usando sensores associados quando todos forem da mesma horta. Eventos mistos devem ser separados com mapa evento original → eventos novos, conservando descrição/autoria e cada leitura; eventos sem sensor exigem atribuição manual. Autoria não informa a horta, pois usuário pode ter várias. Leituras de `monito_sensor` repetidas no mesmo evento/sensor exigem separar amostras com identificação rastreável, não descartar. Converter valores/tipos/unidades sem arredondamento não documentado.
12. Executar INSERTs no destino em transação por lote verificado, na ordem de dependências do schema. Resolver IDs com os mapas. Sem DDL dentro da transação de dados. Registros pendentes permanecem em staging; **não realizar corte enquanto houver entidade necessária sem destino**.
13. Reconciliar por entidade: contagem original, contagem de destino, desdobramentos/consolidações aprovados e pendências, somas/intervalos numéricos e vínculos de cada PK. Verificar amostras e histórico integral, incluindo payloads que não couberam no modelo novo. Executar `verificar.sql` e os testes de integridade em cópia.
14. Integrar repositórios PDO/autenticação em etapa posterior. Com ambas as fontes congeladas, realizar última reconciliação, configurar a aplicação no novo banco, testar fluxos e liberar escritas. Manter origem e mapas para auditoria. Rollback anterior a novas escritas é voltar à fonte antiga; depois de novas escritas requer exportação/reconciliação reversa, nunca apagar tabelas para tentar voltar.

Alterações futuras do schema devem receber migrações numeradas novas e atualizar `schema_version` somente após sucesso. `hydroponex.sql` é instalador, não migração de atualização. A preservação da origem e dos mapas resolve os casos em que uma transformação 1:N ou N:N exige intervenção de domínio em vez de perda silenciosa de informação.
